# 2D 数字人形象自制执行指南

## 1. 文档目的

本文档用于指导团队成员自制并替换本项目的 2D 数字人形象素材，覆盖从角色设定、绘制导出、后台上传到游客端验证的完整流程。

## 2. 当前项目形象机制

当前项目的数字人展示由三部分组成：

1. 图片形象素材
   - 后台“数字人素材管理”可上传 `PNG`、`WebP`、`AVIF`、`GIF`、`JPG/JPEG`。
   - 游客端优先展示后台上传后的形象。
   - 透明背景优先，推荐 `PNG`、`WebP`、`AVIF` 或 `GIF`。
   - `JPG/JPEG` 可用，但照片背景会一并显示。

2. 前端动效
   - 当前游客端会根据“聆听、思考、播报”等状态切换 CSS 动效。
   - 静态图片素材本身不具备真实骨骼、分层口型或表情变形。

3. 可选云端视频
   - 后端接入外部数字人视频服务后，问答接口可返回 `video_url` 和 `video_status`。
   - `video_status=ready` 时优先播放视频。
   - 视频失败、超时或未启用时，自动回退到音频和前端动效。

当前项目不是 Live2D Cubism 模型。Live2D Cubism 模型 = 将角色拆成头发、脸、眼睛、嘴、身体、手臂等图层后，通过 Live2D Cubism 制作可绑定动作参数的分层骨骼模型。当前项目第一版使用的是图片形象素材。

## 3. 角色定位

数字人应定位为“景区 AI 导览员”，不是普通聊天角色、游戏角色或虚拟偶像复刻。设计时优先表达以下特征：

1. 身份清晰
   - 一眼能看出是景区导览服务角色。
   - 可加入胸牌、导览证、耳麦、讲解器、地图夹、服务标识等元素。
   - 不建议使用过度战斗、偶像舞台、校园制服等偏离景区服务的设定。
2. 气质稳定
   - 表情亲和，姿态端正。
   - 适合对游客讲解路线、文化、礼仪和景点信息。
   - 不做夸张诱导、玄学承诺或神秘化表情。
3. 文化适配
   - 可以参考景区建筑、山水、莲花、导览标识等抽象元素。
   - 不直接复制佛像、宗教法器、真实僧侣形象或具有宗教承诺意味的符号组合。

## 4. 推荐视觉方案

### 4.1 基础形象

全身形象或二次元人物形象。

推荐元素：

- 头部：清晰脸部、温和微笑、眼神朝向用户。
- 服饰：可以采用导览员服装，可加入青绿色、金色、湖蓝色点缀。
- 胸牌：可写 `GUIDE`、`AI` 或景区导览标识。
- 背景：透明背景优先，不把复杂景区照片画进角色素材里。

不推荐元素：

- 大面积文字塞进衣服或头饰。
- 过度复杂的细碎纹样，移动端会糊成噪点。
- 黑色大阴影、强光晕、复杂背景。

### 4.2 色彩建议

建议主色不超过 3 个：

- 主色：青绿、湖蓝、暖白等稳定文旅色。
- 辅色：金色、浅黄色等用于胸牌、发饰、按钮呼应。
- 中性色：深灰、米白、浅灰用于服饰层次。

避免整张图只有单一紫色、单一棕色或过度霓虹色。游客端当前页面是深色艺术风格，角色需要有足够明度和轮廓线，避免贴上去后看不清。

## 5. 制作流程

### 5.1 第一步：写角色设定

先写 5 行设定，再开始画图或生成图片。

模板：

```text
角色名称：灵灵 / 云溪 / 景区导览 AI
角色身份：景区 AI 导览员
服务场景：游客问答、路线讲解、景点讲解、礼仪提示
视觉关键词：亲和、专业、文旅、清爽、可信
禁用元素：第三方 IP、真人肖像、宗教功效承诺、占卜预测暗示
```

### 5.2 第二步：画草图

草图只解决构图，不追求细节。

草图检查点：

- 角色站位是否居中。
- 头部是否占主体高度的 25% 到 35%。
- 表情是否友好。
- 胸牌或导览标识是否看得清。
- 双手是否不会遮挡脸部。

### 5.3 第三步：线稿和上色

线稿要求：

- 外轮廓清楚，移动端缩小时仍能识别。
- 脸部、眼睛、嘴巴不要画得过小。
- 胸牌和手势要简化。

上色要求：

- 先铺大色块，再加少量阴影。
- 阴影层级控制在 1 到 2 层。
- 不做复杂材质和高频纹理。

### 5.4 第四步：去背景

推荐透明背景。透明背景能让角色自然融入游客端舞台，不会出现白底方块。

工具选择：

- Photoshop：选择主体后建立蒙版，再导出透明 PNG。
- Clip Studio Paint：隐藏背景图层，导出 PNG。
- Procreate：关闭背景色，导出 PNG。
- Canva：使用去背景功能后导出 PNG。
- AI 绘图工具：生成后仍建议用图像软件检查边缘和透明通道。

去背景检查：

- 头发边缘没有白边或黑边。
- 手指、发饰、衣袖没有被误删。
- 角色脚下或身体周围没有多余阴影块。
- 背景确实透明，不是白色或灰色画布。

### 5.5 第五步：导出素材

推荐导出规格：

```text
画布比例：3:4 或 4:5
建议尺寸：900 x 1200、1200 x 1600、1440 x 1920
最低高度：900px
推荐格式：PNG 或 WebP
备选格式：AVIF、GIF、JPG/JPEG
文件命名：avatar_lingling_v1.png
```

文件命名要求：

- 使用英文、数字、短横线或下划线。
- 不使用空格。
- 不使用中文标点。
- 推荐带版本号，例如 `avatar_guide_v1.png`、`avatar_guide_v2.webp`。

JPG/JPEG 使用限制：

- JPG 不支持透明背景。
- 上传 JPG 后，游客端会显示图片原背景。
- 只有在素材本身已经做成完整海报或照片风格时才建议使用 JPG。

GIF 使用限制：

- GIF 可用于简单眨眼、挥手等循环动效。
- 文件体积不宜过大。
- 不建议使用高频闪烁、快速抖动或强烈跳动效果。

## 6. 使用 AI 辅助生成时的要求

可以使用 AI 绘图辅助生成原创角色，但必须控制版权和相似性风险。

推荐提示词方向：

```text
原创景区 AI 导览员，2D 半身角色，亲和微笑，现代文旅制服，青绿色和金色点缀，胸牌写 GUIDE，手持导览地图，透明背景，干净线稿，移动端清晰，原创角色设计，不模仿任何现有 IP 或真人
```

禁止提示词方向：

```text
像某某明星
像初音未来
某游戏角色同款
某动漫角色风格完全一致
真实宗教人物
保证许愿灵验
招财改运占卜
```

AI 生成后必须人工复核：

- 发型、配色、服装是否明显接近已有角色。
- 脸部是否像真实人物或公众人物。
- 服饰是否包含不可授权商标、校徽、品牌 Logo。
- 是否出现宗教功效暗示、占卜道具或许愿承诺文字。

## 7. 后台上传流程

启动项目后访问：

```text
http://127.0.0.1:8000/app/
```

操作步骤：

1. 点击顶部“管理端”。
2. 使用默认账号登录：`admin / admin123`。
3. 找到“数字人形象管理”。
4. 在“数字人素材管理”区域选择素材文件。
5. 点击“上传形象素材”。
6. 上传成功后切回“游客端”。
7. 确认游客端舞台显示新角色。

上传成功后的系统行为：

- 后端保存文件到生成目录。
- 后端更新当前数字人的 `avatar_asset_url`。
- 数字人主题切换为 `asset-avatar`。
- 游客端优先展示上传后的形象。

## 8. 游客端验证标准

上传后必须做以下检查：

1. 桌面端检查
   - 角色完整显示。
   - 脸部、胸牌、手势清楚。
   - 没有白底方块。
   - 没有遮挡问答区、输入框、发送按钮。

2. 移动端检查
   - 390px 宽度下无横向滚动。
   - 角色不挤压页面标题。
   - 角色不遮挡讲解模式按钮。
   - 角色不遮挡问答输入区。

3. 内容检查
   - 素材无第三方 IP。
   - 素材无未经授权真人肖像。
   - 素材无宗教功效承诺。
   - 素材无占卜预测暗示。

4. 演示检查
   - 提问后能正常回答。
   - 音频播放时视觉状态正常。
   - 外部视频未启用时仍能回退到音频和前端动效。

## 9. 常见问题处理

### 9.1 上传后角色有白底

原因：素材不是透明背景，或导出成了 JPG。

处理：重新导出透明 PNG/WebP，确认背景图层已关闭。

### 9.2 角色边缘有白边

原因：去背景时边缘残留。

处理：使用蒙版细修边缘，或在透明背景上手动擦除残边。

### 9.3 移动端角色太大

原因：图片主体离画布边缘太近，前端缩放后视觉占比过大。

处理：扩大画布留白，让头顶、左右手臂、衣摆周围有安全边距。

### 9.4 角色太糊

原因：导出尺寸过低或压缩过度。

处理：重新导出高度 1200px 以上版本，优先 PNG 或高质量 WebP。

### 9.5 角色不像导览员

原因：缺少服务身份元素。

处理：加入胸牌、导览证、耳麦、地图夹、讲解器或统一制服元素。

## 10. 升级路线

### 10.1 静态立绘版

适合当前项目第一版交付。

特点：

- 成本低。
- 制作快。
- 后台上传即可替换。
- 配合前端状态动效和音频播报即可演示。

### 10.2 GIF 简单动效版

适合增加轻量动感。

可做动效：

- 眨眼。
- 轻微挥手。
- 胸牌闪光。
- 头部轻微点动。

限制：

- GIF 不能做精准口型同步。
- 文件过大会影响加载。
- 动作循环要平稳，避免干扰游客阅读。

### 10.3 分层 Live2D 预备版

适合后续升级到正式 Live2D。

制作时需要保留分层源文件：

```text
head
hair_front
hair_back
face
eye_left
eye_right
mouth
body
arm_left
arm_right
badge
accessory
```

交付要求：

- 保留 PSD 或 Clip Studio 源文件。
- 图层命名清楚。
- 左右眼、嘴巴、手臂分开。
- 不把所有元素合并成一张图。

当前项目不直接加载 Live2D Cubism 模型，如需升级，需要另行增加前端 Live2D SDK 或使用外部渲染服务。

### 10.4 外部视频数字人服务版

适合追求口型同步和真实播报效果。

流程：

1. 项目后端生成问答文本和 `audio_url`。
2. 后端把 `text`、`audio_url`、`avatar_id` 发给外部数字人视频服务。
3. 外部服务返回 `video_url`。
4. 游客端优先播放视频。
5. 视频失败时回退音频和 2D 立绘。

该路线适合低显卡客户端发行，因为 EXE/APK 不内置模型，只加载云端页面。

## 11. 交付清单

每次交付一个新 2D 数字人形象时，至少提供：

```text
avatar_guide_v1.png
avatar_guide_v1_source.psd 或其他源文件
设计说明 5 行
授权说明或自制声明
游客端截图 1 张
移动端 390px 截图 1 张
```

设计说明模板：

```text
角色名称：
角色身份：
主色方案：
使用场景：
授权状态：自制 / 已授权
```

## 12. 答辩说明口径

答辩时可这样说明：

```text
本项目第一版数字人采用 2D 原创立绘 + 前端状态动效 + 语音播报的方式实现，后台支持上传自制或已授权图片素材，并可配置名称、身份、声线、欢迎语和服务边界。考虑到低显卡发行版目标，EXE 和 APK 不内置大型数字人模型；当云端外部视频服务可用时，游客端优先播放数字人视频，失败时自动回退到音频和 2D 立绘动效。后续可在保留当前问答链路的基础上升级为 Live2D 分层模型或视频数字人服务。
```

必须主动说明的边界：

- 当前不是 3D 数字人。
- 当前不是 Live2D Cubism SDK 模型。
- 当前默认口型同步是播放状态驱动，不是音素级口型。
- 项目不内置第三方 IP、未经授权真人肖像或宗教功效承诺类素材。
