## 第 2 页：项目目标与核心策略

**标题**：项目目标与核心策略

**副标题**：先闭环、再增强、先保正确、再追求表现力

### 题目要求理解

赛题不是让做一个什么都能聊的模型，而是要求构建一套能在景区场景里闭环工作的系统：
- 游客可以通过文本、语音、图片提问
- 系统能基于本地景区知识给出可靠导览回答
- 能支持语音播报和数字人讲解展示
- 后台能看到知识库管理、日志记录和评测结果

### 项目需求拆解为五类

| 类别 | 具体内容 |
|------|----------|
| 游客服务能力 | 文本问答、语音问答、路线推荐、景点讲解、礼仪提示、英文讲解 |
| AI 能力支撑 | 本地知识库、RAG 向量检索、多模态视觉模型、主模型生成/补救 |
| 数字人表达 | 语音合成、口型同步、表情反馈、真人数字人视频讲解 |
| 后台运营 | 知识库管理、日志查看、反馈统计、状态监控、自动评测 |
| 工程交付 | 本地可运行、Git 可协作、文档可交接、可打包部署 |

### 研发总策略

1. A 端后端闭环：先把文本问答、知识库、日志、管理后台跑通
2. 知识优先于生成：事实类问题尽量由本地知识库和 RAG 约束，避免大模型乱编
3. 展示层逐步增强：语音、数字人、H5 视觉、图片识别在闭环基础上逐个接入
4. 失败可降级：任何增强模块失败都不能把主问答链路拖垮

**讲述者口头重点**（30秒）：
> 我们拿到题目后做的第一个判断是——这不是聊天机器人，是景区导览闭环系统。所以策略定为先保正确再追求表现力，先做后端闭环、知识库，再逐步加语音和数字人。所有增强组件都可以降级，主问答链路不能崩。

### 技术选型与理由

| 组件 | 选型 | 为什么这么选 |
|------|------|-------------|
| Web 框架 | FastAPI | 自带 /docs 接口文档，答辩可直接展示；Python 生态接模型、TTS、文件处理方便 |
| 数据库 | SQLite | 零安装、零配置，复刻一条命令跑通；规模够用；方便打包提交 |
| 向量存储 | SQLite JSON 字段 | 知识库几百条规模，不需要 Chroma/FAISS/Milvus；减少额外服务依赖 |
| Embedding 模型 | BAAI/bge-m3 | 中文语义效果好；OpenAI 兼容接口，换模型不改代码 |
| 中文主模型 | GLM-5.1 | 中文表达自然；仅做补救不做主生成，超时设为 0.9 秒极限控制 |
| 多模态模型 | GLM-4.5V | 赛题硬要求"至少一个多模态大模型"；视觉识别效果稳定 |
| 语音合成 | 浏览器本地朗读 + Edge TTS | 本地朗读即时响应；Edge TTS 音质好但慢(11-13秒)，用缓存解决 |
| 数字人 | LiteAvatar sidecar | 真人口型视频；不接管问答链路；失败可降级为音频 |
| 前端 | 原生 HTML/CSS/JS | 不增加 npm 构建链路；FastAPI 直接挂载静态资源；手机 H5 适配 |

### 核心设计原则：失败可降级

```
降级链路一（回答生成）：
  RAG 向量检索 → 纯关键词检索 → LLM 修复 → fallback 模板 → gap 提示

降级链路二（语音播放）：
  数字人视频 MP4 → 服务端 TTS 音频 → 浏览器本地语音(Web Speech API)

降级链路三（TTS 生成）：
  本地 MOSS-TTS-Nano(:18083) → Edge TTS 缓存命中 → Edge TTS 实时生成

降级链路四（唇形同步）：
  Rhubarb viseme JSON 时间轴 → Web Audio RMS 实时分析 → 无唇形
```

## 第 4 页：核心能力① — 知识库与 RAG

**标题**：核心能力① — 本地知识库与 RAG 检索

**副标题**：解决"大模型乱编景区事实"的核心问题

### 为什么不直接让大模型回答

| 问题 | 说明 |
|------|------|
| 事实可能编造 | 问"灵山大佛多高"，模型可能编一个数字 |
| 路线可能瞎推 | 模型没去过灵山，推荐路线可能把不存在的景点加进来 |
| 不可复现 | 同样问题每次回答不同，答辩时不可控 |
| 无法验证来源 | 老师问"这个信息哪来的"，说不出知识来源 |

**结论**：景区导览必须以本地知识库为事实基础，大模型只做语言组织和表达增强。

### RAG 检索完整链路

```
用户输入问题
    │
    ▼
┌─────────────────────────────────────┐
│ 1. 当前景区过滤                      │  只检索灵山胜境相关片段
├─────────────────────────────────────┤
│ 2. Query Embedding (bge-m3)         │  将问题转为 768 维向量
├─────────────────────────────────────┤
│ 3. 向量召回 (cosine similarity)      │  从 SQLite JSON 向量索引中召回
├─────────────────────────────────────┤
│ 4. 关键词召回补充                    │  分词匹配，补充向量可能遗漏的结果
├─────────────────────────────────────┤
│ 5. 混合评分重排                      │  向量分 + 关键词加分(上限0.1)
├─────────────────────────────────────┤
│ 6. 过滤非导览内容                    │  去掉目录、页眉、字段说明等噪声
├─────────────────────────────────────┤
│ 7. 过滤非当前景区片段                │  去掉其他景区的干扰内容
├─────────────────────────────────────┤
│ 8. 取 top_k 片段作为上下文           │  只用最相关的几条组织回答
├─────────────────────────────────────┤
│ 9. 本地抽取式回答                    │  从检索结果中直接提取答案
├─────────────────────────────────────┤
│ 10. 回答验证                         │  检查答案质量和完整性
├─────────────────────────────────────┤
│ 11. 验证失败 → LLM 修复（0.9秒超时） │  GLM-5.1 仅在本地不够时补救
├─────────────────────────────────────┤
│ 12. 全部失败 → fallback 模板         │  保底回答，不让用户看到空白
└─────────────────────────────────────┘
```

### 关键技术细节

| 参数/机制 | 具体值 | 说明 |
|-----------|--------|------|
| Embedding 模型 | BAAI/bge-m3 | 中文多语言，768 维度 |
| Embedding 接口 | OpenAI 兼容 API | 配置 base_url 和 key 即可切换 |
| 向量存储 | SQLite JSON 字段 | 每条知识片段存一个 JSON 数组作为向量 |
| 相似度算法 | Cosine Similarity | 标准余弦相似度 |
| 关键词加分 | min(keyword_score, 2.0) × 0.05 | 叠加到向量分上，防止纯语义遗漏 |
| 嵌入批量大小 | batch_size = 16 | 每次请求最多 16 条文本 |
| 嵌入重试策略 | 3 次重试，0.6 秒退避 | 网络波动时自动恢复 |
| 嵌入超时 | 45 秒 | 单次请求最大等待时间 |
| LLM 修复超时 | min(配置值, 0.9) 秒 | 极限压缩，不让模型拖慢响应 |
| 噪声过滤 | _is_structural_noise() | 过滤目录、页眉页脚、字段定义 |
| 景区过滤 | _belongs_to_current_scenic() | 只保留当前景区内容 |

### 降级保障

```
正常路径：bge-m3 向量检索 + 关键词补充 → 混合重排 → 本地抽取回答
    │
    │ （如果 Embedding API 不可用）
    ▼
降级路径：纯关键词检索 → 模板回答
    │
    │ （如果本地抽取质量不够）
    ▼
LLM 修复：GLM-5.1 基于检索上下文组织语言（0.9秒超时）
    │
    │ （如果 LLM 也超时或不可用）
    ▼
兜底：fallback 模板回答 / gap 提示
```

### 知识库管理能力

- 后台支持上传 .docx / .xlsx 景区资料，自动切片入库
- 管理员可在线新增、编辑、删除知识片段
- 支持一键重建向量索引 (POST /api/admin/rag/rebuild)
- 支持查看 RAG 状态：索引片段数、最后重建时间、Embedding 服务状态

### 开发中踩过的坑

| 问题 | 原因 | 解决 |
|------|------|------|
| "灵山大佛"和"灵山胜境"互相干扰 | 关键词重叠 | 加景区级别过滤，区分景区和景点 |
| 数据集字段说明被当成导览内容召回 | 没有区分文档类型 | 加 _is_structural_noise() 过滤 |
| Embedding 偶尔超时导致整个问答卡住 | 同步等待 | 改为超时降级到关键词检索 |
| 多次重复问题每次都调 Embedding | 没有缓存 | 加查询向量缓存 |

**讲述者口头重点**（40秒）：
> 我们为什么不直接让大模型回答？因为景区导览要的是事实准确，模型可能编造数据。所以我们用本地知识库和 RAG 做事实基础，大模型只在本地回答不够好的时候做0.9秒限时补救。检索用的是 bge-m3 向量 + 关键词混合召回，过滤掉噪声后重排取 top-k。如果向量服务挂了，自动降到关键词检索，保证系统不崩。

## 第 5 页：核心能力② — 多模态图片识别导览

**标题**：核心能力② — GLM-4.5V 图片识别导览

**副标题**：满足赛题"至少使用一个多模态大模型"的硬要求

### 为什么需要图片识别

- 赛题明确要求：至少使用一个多模态大模型作为核心 AI 能力支撑
- 实际场景：游客看到一个景点想了解，但不知道名字，拍照上传最直觉
- 作为系统多模态能力的硬证据，答辩时可以现场演示

### 图片导览完整链路

```
游客拍照/上传图片
    │
    ▼
┌─────────────────────────────────────┐
│ 1. 图片预处理                        │  校验大小(≤8MB)、格式
├─────────────────────────────────────┤
│ 2. 发送到 GLM-4.5V                  │  视觉模型识别画面内容
├─────────────────────────────────────┤
│ 3. 识别候选景点                      │  模型输出"这张图里可能是九龙灌浴"
├─────────────────────────────────────┤
│ 4. 与本地景点列表匹配                │  确认是否为已知景点
├─────────────────────────────────────┤
│ 5. 构造导览问题                      │  将识别结果转化为知识库查询
├─────────────────────────────────────┤
│ 6. RAG 检索知识库                    │  用本地事实生成讲解，不让视觉模型编
├─────────────────────────────────────┤
│ 7. 生成中文讲解回答                  │  基于检索结果组织导览语言
├─────────────────────────────────────┤
│ 8. 触发语音 + 数字人讲解              │  和文本问答走同一条输出链路
└─────────────────────────────────────┘
```

### 关键设计思想

**视觉模型只负责"看"，不负责"讲"**

- GLM-4.5V 的职责：告诉系统"图里是什么"
- RAG 的职责：提供这个景点的准确事实
- 主模型的职责：组织自然语言讲解

这样设计的好处：
- 视觉模型不会编造景区信息
- 事实来源始终是本地知识库，可追溯
- 老师问"信息哪来的"可以清楚说明

### 技术配置

| 配置项 | 值 | 说明 |
|--------|------|------|
| ENABLE_VISION_GUIDE | true | 开启图片识别功能 |
| VISION_MODEL_BASE_URL | https://api.edgefn.net/v1 | 视觉模型接口地址 |
| VISION_MODEL_NAME | GLM-4.5V | 必须大写，小写会 ModelNotFound |
| VISION_MODEL_TIMEOUT_SECONDS | 20 | 视觉识别超时 |
| VISION_IMAGE_MAX_MB | 8 | 上传图片最大尺寸 |

```
响应：{
```

### 开发中踩过的坑

| 问题 | 原因 | 解决 |
|------|------|------|
| /api/chat/image 返回 500 | Windows 环境变量 no_proxy=...::1/128 导致 httpx 报 Invalid port ':1' | 视觉请求中设置 trust_env=False |

| 视觉模型编造景区历史 | 让视觉模型直接生成讲解 | 改为只做识别，事实走 RAG |

**讲述者口头重点**（35秒）：
> 赛题要求至少一个多模态大模型，我们用 GLM-4.5V 做图片识别导览。关键设计是视觉模型只负责"看"——告诉系统图里是什么景点，然后事实讲解仍然走 RAG 从知识库取。这样视觉模型不会编造景区信息。现场可以演示：上传一张灵山的照片，系统识别出景点名，然后给出基于知识库的讲解。

## 第 6 页：核心能力③ — 语音与数字人

**标题**：核心能力③ — 语音合成与数字人讲解

**副标题**：从 13 秒等待优化到即时响应；从 2D 原型迭代到真人口型视频

### 语音延迟问题与解决

**原始问题**：Edge TTS 同步生成 MP3 实测需要 11-13 秒，游客问完问题干等十几秒不可接受。

**排查结论**：文本问答本身 1 秒内出结果，慢的全是 TTS 生成环节。

**解决思路**：不是"换更快的TTS"，而是**解耦文字和语音**，让游客先看到答案。

### 语音策略四层架构

```
┌─────────────────────────────────────────────────────────┐
│ 第一层：文字即时返回                                      │
│ /api/chat/text 先返回文字答案，前端立即渲染聊天气泡        │
│ 游客看到答案的等待时间 ≈ 问答生成时间（通常 < 2秒）        │
├─────────────────────────────────────────────────────────┤
│ 第二层：浏览器本地朗读（即时）                             │
│ 使用浏览器 Web Speech API (speechSynthesis)              │
│ 优点：零延迟开始播报，不依赖服务端                         │
│ 缺点：音色受系统语音包限制，部分手机 WebView 不支持        │
├─────────────────────────────────────────────────────────┤
│ 第三层：服务端 Edge TTS 缓存命中（近乎即时）               │
│ 缓存键 = SHA256(文本 + voice_name + 版本 + max_chars)    │
│ 缓存目录：data/generated/audio/cache/                    │
│ LRU 策略：最多保留 300 条，超出自动清理最旧文件            │
│ 预热脚本：50题评测集 + 热门问题 + 推荐chip + 欢迎语       │
├─────────────────────────────────────────────────────────┤
│ 第四层：Edge TTS 实时生成（兜底，11-13秒）                 │
│ 仅在缓存未命中且本地朗读不可用时触发                       │
│ 异步生成，前端轮询 GET /api/chat/audio/{log_id}          │
│ 轮询间隔 700ms，最多 60 次（42秒超时）                    │
└─────────────────────────────────────────────────────────┘
```

### 前端播放优先级逻辑（实际代码）

```javascript
if (videoReady) {
    // 最优：数字人视频已就绪，直接播放带口型的 MP4
    playDigitalVideo(videoPlaybackUrl(data), data.audio_url);

    playLocalAnswer(data, { autoPlay: true });

} else if (data.audio_status === "pending") {
    // 服务端音频生成中，轮询等待
    pollAnswerAudio(data.log_id, { autoPlay: true });
}
```

### 数字人迭代历程

| 阶段 | 方案 | 结果 |
|------|------|------|
| V1 | 自制 SVG + CSS 表情动画 | 视觉粗糙，恐怖谷效应 |
| V2 | 2D 仿生面部关键点 Rig + Web Audio RMS 驱动 | 技术路线验证成功，但美术不足 |
| V3 | OpenAvatarChat 完整 UI | 功能重复太多，资源占用高，像拼接 |
| V4（当前） | LiteAvatar avatar-only sidecar | 只负责"音频→口型视频"，不接管问答 |

### LiteAvatar avatar-only sidecar 工作方式

```
A5 问答生成文字答案
    │
    ▼
A5 服务端生成语音 MP3（Edge TTS）
    │
    ▼
发送音频到 LiteAvatar sidecar (:18085)
    │
    ▼
LiteAvatar 生成真人数字人口型讲解 MP4
    │
    ▼
A5 游客端播放 MP4（数字人舞台区域）
```

**设计关键**：
- sidecar 不接管 A5 的 LLM、RAG、ASR 或后台
- sidecar 只做一件事：输入音频 → 输出带口型的人物视频
- 失败时自动降级为语音讲解 + 2D 待命循环视频，不影响主链路
- 待命状态播放 LiteAvatar 静音动态循环视频，避免空白

### 唇形同步两种实现

| 方式 | 技术 | 适用场景 |
|------|------|----------|
| Rhubarb viseme 驱动 | 预生成 JSON cue 文件，按时间戳驱动 CSS 口型变量 | 有服务端音频时，精度高 |
| 实时 RMS 分析 | Web Audio API, fftSize=1024, smoothing=0.58，振幅映射口型开合 | 本地朗读时，无需预处理 |

### 服务端 TTS 后端实现细节

| 参数 | 值 | 说明 |
|------|------|------|
| TTS 提供者优先级 | moss_onnx(:18083) → edge_tts | MOSS 本地优先，Edge 兜底 |
| Edge TTS 默认语音 | zh-CN-XiaoxiaoNeural | 中文女声 |
| 英文语音 | 独立配置 ENGLISH_TTS_VOICE | 可选英文声线 |
| 缓存 LRU 上限 | 300 条 | 超出自动删除最旧缓存 |
| 音频后台任务 | daemon 线程异步执行 | 不阻塞主请求响应 |
| 任务链路 | 生成TTS → lipsync cue → 数字人视频 | 串行执行 |

**讲述者口头重点**（35秒）：
> 语音最大的坑是 Edge TTS 同步生成要 11-13 秒。我们的解决方案不是换 TTS，而是解耦——文字先返回让游客看到，浏览器本地朗读即时播报，服务端异步生成音频存缓存。数字人从 2D 原型迭代到 LiteAvatar，它只负责一件事：把音频变成带口型的视频。挂了就退回语音，不影响主链路。
