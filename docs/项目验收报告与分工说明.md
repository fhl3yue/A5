> 适用场景：下周一验收、课堂答辩、老师追问、队友分工准备  
> 项目入口：`http://127.0.0.1:8000/app/`  
> 后端接口文档：`http://127.0.0.1:8000/docs`  
> 当前推荐提交分支：`codex/a5-research-doc-20260623`

## 1. 项目定位

本项目是一个面向景区导览场景的 AI 数字人系统，当前以“灵山胜境”为示范景区。系统不是普通聊天机器人，也不是只展示头像的前端页面，而是一个完整的导览闭环：游客可以通过文本、语音、图片提出问题，系统基于本地景区知识库和多模态模型生成回答，再通过数字人语音、表情和口型同步进行表达，后台还能查看知识库、日志、满意度、评测结果和服务状态。

项目的核心取向是“导览准确性优先，展示效果其次，工程稳定性兜底”。因此，系统没有把所有问题都交给大模型自由回答，而是采用“本地知识库 + RAG + 模板 + 主模型补救 + 数字人表达”的组合策略。

## 2. 赛题要求对照

### 2.1 功能性需求

1. 多模态交互：支持语音输入和文本输入，数字人以语音、表情和口型同步方式回答。
2. 智能问答与讲解：能回答景区历史、文化、景点特色等常见问题。
3. 个性化推荐：可根据游客兴趣推荐游览路线和讲解重点。
4. 管理后台：知识库管理、数字人形象管理、游客感受度报告、数据大屏概览。

### 2.2 非功能性需求

1. 至少使用 1 个多模态大模型作为核心 AI 能力支撑。
2. 构建本地景区知识库，事实问答准确率不低于 90%。
3. 系统稳定，语音问答延迟控制在合理范围内，避免长时间无响应。
4. 可选扩展：考虑 GPS、定位困难等现实场景。

## 3. 项目流程设计思路

本项目采用“先闭环、再增强、最后稳定化”的流程。

### 3.1 为什么先做闭环

比赛/验收最忌讳只做出某一个亮点，却没有整体流程。我们先把游客端、后端、知识库、语音、后台和数字人串起来，让系统至少能跑通一条完整路径：

游客提问 -> 后端理解 -> 知识库检索 -> 回答生成 -> 语音播报 -> 数字人讲解 -> 后台记录与分析。

### 3.2 为什么先做本地知识库

景区导览最怕“瞎编”。如果完全依赖大模型自由生成，事实问答会失控，因此先建立本地景区知识库，再做 RAG 检索和模板回答，保证景区问题的准确性。

### 3.3 为什么先做模板，再做 RAG

模板回答的优点是可控、稳定、便于验收；RAG 的优点是更自然、更有扩展性。项目先用模板把高频问题跑通，再升级为正式 RAG v1，避免一开始就被复杂检索拖慢进度。

### 3.4 为什么数字人后置

数字人是最容易“看起来很强、实际最难稳定”的部分。我们先保住问答和后台，再把数字人从 2D 原型逐步升级到 LiteAvatar 真人口型视频，最终避免把项目卡死在重模型和显存问题上。

## 4. 技术架构

### 4.1 整体架构

```text
游客端 H5 / 管理端
        |
        v
FastAPI 后端
        |
        +-- SQLite 本地数据库
        +-- 本地景区知识库
        +-- SQLite JSON 向量索引
        +-- RAG 检索
        +-- GLM-5.1 中文回答补救
        +-- GLM-4.5V 图片识别导览
        +-- 英文翻译服务
        +-- 浏览器本地朗读 / Edge TTS 缓存
        +-- LiteAvatar avatar-only sidecar
        |
        v
数字人讲解、后台统计、评测与日志
```

### 4.2 后端技术选型

| 技术 | 用途 | 选择原因 |
|---|---|---|
| FastAPI | 后端主框架 | 接口清晰、文档自动生成、适合联调和答辩 |
| SQLite | 本地数据库 | 轻量、易部署、适合比赛演示 |
| SQLAlchemy | ORM | 简化数据访问与表结构管理 |
| RAG + Embedding | 知识检索 | 约束回答事实来源 |
| GLM-5.1 | 中文回答补救 | 增强表达自然度和修复局部答案 |
| GLM-4.5V | 图片理解 | 满足“至少 1 个多模态大模型”要求 |
| edge-tts | 中文语音 | 快速生成高质量语音 |
| faster-whisper | 语音识别 | 支持本地 ASR |
| Rhubarb Lip Sync | 口型时间轴 | 可选口型增强 |
| LiteAvatar sidecar | 真人数字人视频 | 作为最终更接近“真人数字人”的演示路线 |

## 6. 核心模块说明

### 6.1 本地知识库与 RAG

项目使用本地景区知识库维护景点、文化、演出时间、路线等事实信息。RAG 使用 `BAAI/bge-m3` 生成向量，并以 SQLite JSON 形式存储，优点是轻量、可打包、容易复刻。

当前自建 50 题事实测试集结果为 50/50，通过率 100%，P95 响应时间约 1.931 秒。  
答辩时要如实说明：这是自建测试集结果，正式准确率仍以评审专家标准测试集为准。

### 6.2 多模态图片识别

使用 `GLM-4.5V` 处理游客上传的景区图片，先识别“这张图像可能是哪个景点”，再接入本地 RAG 知识库讲解。  
注意：图片不是“知识库图片”，而是输入；真正负责事实准确的是文字知识库。

### 6.3 语音与口型

当前采用三层策略：

1. 浏览器本地朗读优先，最快让游客听到语音。
2. 服务端 Edge TTS 异步回退，手机或本地朗读失败时使用。
3. LiteAvatar avatar-only sidecar 生成真人数字人口型讲解视频，作为更强展示层。

### 6.4 数字人路线

项目早期尝试过 2D/SVG 原型，但效果不够自然。后来评估了完整 OpenAvatarChat，发现 UI、摄像头、RTC 和显存压力太重，不适合作为主线。最终采用 LiteAvatar avatar-only sidecar，只保留“输入音频 -> 输出会动、有口型的人物视频”的能力。

### 6.5 保障稳定性的边界控制

项目现在不是“什么都答”，而是“只对景区导览范围内的问题负责”。对明显超出范围的问题，例如外地天气、外地门票、泛互联网问题，系统会明确回答“当前无法从知识库获取”，而不是强行套景区模板。

这点在验收时很重要，因为它能证明系统不是关键词碰巧命中，而是有边界控制能力。

## 8. 教师最可能追问的问题

### 8.1 为什么不用纯大模型直接回答？

因为景区导览要求事实准确。纯大模型容易自由发挥，我们用本地知识库 + RAG 先约束答案，再用 GLM-5.1 做表达增强或修复。

### 8.2 为什么要做多模态？

赛题明确要求至少 1 个多模态大模型。我们用 `GLM-4.5V` 做图片理解，让游客能上传景区图片并触发导览讲解。

### 8.3 为什么不用更重的向量数据库？

因为当前知识量不大，SQLite JSON 足够，Windows 复刻更稳，比赛/答辩更可靠。后续规模扩大再迁移也不迟。

### 8.4 数字人为什么没有直接上完整 OpenAvatarChat？

完整 OpenAvatarChat 太重，包含摄像头、RTC、ASR、UI 等整套链路，和 A5 的功能重复，且有显存风险。我们抽离 LiteAvatar 作为 avatar-only sidecar，保留真人数字人视频能力但降低风险。

### 8.5 语音为什么有时不是同一个音色？

桌面浏览器优先本地朗读，音色取决于浏览器和系统；服务端则走 Edge TTS 缓存和回退。为了稳定，我们优先保速度与可用性，再追求统一音色。

### 8.6 如果游客问的不相关怎么办？

系统会明确提示“当前无法从知识库获取”或“不启用联网查询”，不再答非所问。这是导览系统必须具备的边界控制。

## 9. 两人分工建议

### 9.1 分工原则

建议按“前后端 / 智能与展示”切分，但要保证每个人都能独立讲完整的一条演示链路。这样老师如果分别提问，任意一个人都能回答，不会出现“只有一半人能讲”的情况。

### 9.2 你负责的部分：A 端与智能能力

你主讲以下内容最合适：

- 项目背景与需求理解
- 后端架构与数据库设计
- 本地知识库与 RAG
- GLM-5.1 / BAAI-bge-m3 / GLM-4.5V 的作用
- 事实准确率与 50 题评测
- 超出范围问题如何拦截
- AI 状态、RAG 状态、后台日志与评测
- LiteAvatar sidecar 的接入思路

你可以重点展示：

1. `POST /api/chat/text`
2. `POST /api/chat/image`
3. `GET /api/admin/ai/status`
4. `GET /api/admin/rag/status`
5. `GET /api/admin/evaluation/latest`

### 9.3 队友负责的部分：B 端与游客体验

队友主讲以下内容最合适：

- 游客端 H5 页面设计
- 文本/语音/图片交互入口
- 推荐问题和路线生成页面
- 反馈、评分、滚动展示
- 数字人舞台、待命层、讲解视频层
- English 按钮与英文讲解展开
- 移动端适配与视觉优化

队友可以重点展示：

1. `/app/` 首页
2. 提问问答
3. 图片上传识别
4. 路线推荐
5. 数字人讲解按钮
6. 反馈与后台切换

### 9.4 如果队友临时不能到场，你怎么接手

你可以按“两段式”讲：

- 第一段讲 A 端：架构、RAG、多模态、评测、稳定性。
- 第二段讲 B 端：H5、交互、数字人、推荐、反馈。
