# A5 景区导览 AI 数字人研发进程文档

> 文档版本：2026-06-22  
> 项目目录：`D:\software`  
> 演示入口：`http://127.0.0.1:8000/app/`  
> 文档用途：用于课程/竞赛提交、答辩说明、队友交接和后续复盘。

## 1. 项目背景与目标理解

本项目来源于“景区导览服务 AI 数字人”方向，核心目标不是做一个普通聊天机器人，也不是单纯展示一个虚拟形象，而是构建一个面向景区游客的智能导览系统。系统需要让游客能够通过文本、语音、图片等方式提出问题，后台基于本地景区知识库和大模型能力生成可靠讲解，再由数字人以语音、表情和口型同步的方式进行回答。

项目当前以“灵山胜境”为示范景区，但系统定位不是只能服务灵山胜境的固定页面。灵山胜境承担的是演示数据和验收场景作用；从架构上看，知识库、景区资料、数字人配置、推荐问题和后台管理都保留了可替换、可扩展的空间。

最初拆解题目时，我们把需求分为五类：

- 游客服务能力：文本问答、语音问答、路线推荐、景点讲解、礼仪提示、英文讲解。
- AI 能力支撑：本地知识库、RAG 检索、多模态模型、主模型生成或补救。
- 数字人表达能力：语音合成、口型同步、表情反馈、真人/视频数字人展示。
- 后台运营能力：知识库管理、日志查看、反馈统计、状态监控、评测结果。
- 工程交付能力：本地可运行、Git 可协作、文档可交接、后续可打包或部署。

因此，研发策略从一开始就确定为“先闭环、再增强、最后打磨体验”。这比一开始追求某个炫酷组件更稳，因为赛题验收看的是完整系统能力，而不是单个页面效果。

## 2. 研发总体路线

项目研发大致经历了以下路线：

1. 先完成 A 端能力底座：FastAPI 后端、SQLite 数据库、基础接口、静态前端挂载。
2. 先用本地知识库和模板问答跑通游客服务闭环。
3. 补齐路线推荐、语音输入、语音播报、游客反馈和管理后台。
4. 将简单关键词问答升级为正式 RAG 检索链路。
5. 接入 GLM-5.1 主模型作为表达增强与补救能力。
6. 接入 BAAI/bge-m3 Embedding，使用 SQLite JSON 存储向量。
7. 增加独立英文翻译与英文语音服务。
8. 增加 GLM-4.5V 图片识别导览，补齐多模态大模型硬证据。
9. 针对 Edge TTS 过慢问题，改成浏览器本地朗读优先、服务端异步音频回退、Edge TTS 缓存预热。
10. 数字人从 2D 原型尝试转向 OpenAvatarChat/LiteAvatar avatar-only sidecar。
11. 游客端从 Demo 面板重构为手机优先 H5 页面。
12. 补充启动脚本、复刻文档、打包说明和提交材料。

这条路线的核心思想是：所有外部模型和数字人能力都可以失败降级，但游客端文本问答、知识库检索和后台管理不能崩。也就是说，系统优先保证“能稳定回答”和“能完整演示”，再追求更高质量的语音和数字人表现。

## 3. 阶段一：A 端后端能力底座

项目起点是从 `D:\software` 目录开始搭建后端。由于两名成员不在同一地点协作，本人主要负责 A 端，也就是后端服务、知识库、AI 调用和接口闭环。

后端选择 FastAPI，原因如下：

- 自动生成 `/docs` 接口文档，便于开发、测试和答辩展示。
- Python 生态适合快速接入大模型、TTS、文件处理、RAG 和 SQLite。
- 与静态前端结合简单，可以直接将游客端挂载到 `/app/`。
- Windows 本地运行成本较低，方便课程演示。

数据库选择 SQLite，原因如下：

- 不需要安装独立数据库服务，队友复刻更简单。
- 足够支撑当前知识库、问答日志、反馈、配置、向量缓存等数据规模。
- 方便打包、备份和提交演示数据。
- 后续如需扩展，可再迁移到 MySQL、PostgreSQL 或专业向量数据库。

这一阶段完成了健康检查、文本问答、语音上传、路线推荐、反馈提交、管理员登录、日志查询、后台看板等基础接口。接口完成后，前端可以稳定调用，项目从“想法”进入“可运行系统”状态。

## 4. 阶段二：从关键词问答到可控本地导览

早期问答并没有直接使用大模型自由生成，而是先采用本地景区资料、关键词匹配和模板回答。这样做的原因不是认为关键词检索足够先进，而是为了快速形成可控闭环。

早期重点测试的问题包括：

- 灵山胜境在哪里？
- 九龙灌浴几点开始表演？
- 灵山大佛有什么文化含义？
- 半天时间怎么游览？
- 有无停车地点？

这套方案的优点是稳定、响应快、不容易胡说，适合最初演示。但随着问题增多，暴露出几个明显问题：

- 关键词重叠不等于语义相关。
- 有时能找到相关片段，但回答没有按问题重点组织。
- 字段规范、景点 ID、数据集说明可能被误当成导览内容。
- 跨景区或非导览资料可能干扰推荐结果。
- 固定模板容易出现答非所问的感觉。

这些问题推动了后续 RAG 升级。项目也在这一阶段明确：景区导览不能依赖大模型凭空发挥，必须围绕本地景区知识库构建回答。

## 5. 阶段三：路线推荐与轻量个性化

题目要求个性化推荐，但真实推荐系统需要大量用户行为数据。当前项目处于课程/竞赛原型阶段，没有长期游客行为、停留时长、购买记录或 GPS 轨迹，因此不适合一开始就做复杂推荐算法。

本项目采用了轻量但可解释的推荐策略：

- 根据游客输入识别兴趣方向，如历史文化、佛教文化、自然风光、亲子休闲等。
- 根据游览时长生成半天、一日等路线。
- 结合游客最近问答日志提取兴趣关键词。
- 返回推荐路线、讲解重点和匹配原因。

这样做的好处是输出稳定，老师容易理解，也能说明个性化依据。后续如果接入真实游客数据，可以继续在当前结构上升级协同过滤、画像推荐或 GPS 场景推荐。

## 6. 阶段四：前端从功能面板到游客 H5

前端一开始使用原生 HTML、CSS、JavaScript，而没有引入 React、Vue 或大型 UI 框架。主要原因是：

- 页面结构相对可控，原生实现足够支撑演示。
- 不增加 npm 构建链路，降低 Windows 本地运行风险。
- FastAPI 可直接挂载静态资源，部署简单。
- 页面需要频繁根据用户反馈微调，原生 CSS 调整更直接。

早期前端偏功能堆叠，重点是证明接口能用。后续根据实际体验逐步做了多轮重构：

- 去掉过强的科技网格和硬边框，改为深色渐变和毛玻璃风格。
- 将游客端和管理端信息区分，游客端不显示 Key、RAG、模型名等工程信息。
- 问答区改为真实聊天气泡，用户靠右，数字人回答靠左。
- 推荐问题从大卡片改为横向 chip，减少视觉干扰。
- 评分区从大号星星改为“有帮助 / 不准确 / 答非所问”等低调反馈标签。
- 输入区整合为统一输入栏，包含文本、语音、上传、发送等入口。
- 针对手机尺寸 `390x844`、`430x932` 做 H5 优化。

这一阶段的目标从“能点”变成“像一个成熟游客产品”。游客端只呈现游客需要知道的信息，后台状态和技术细节放到管理端。

## 7. 阶段五：正式 RAG 检索层升级

当关键词问答无法满足准确性和自然度要求后，项目升级为正式 RAG v1。RAG 设计目标是：先从本地景区知识库中找可靠资料，再组织导览回答。

本项目没有引入 Chroma、FAISS、Milvus 等向量数据库，而是选择 SQLite JSON 存储向量，原因如下：

- 当前景区知识库规模有限，SQLite JSON 足够支撑演示。
- 减少依赖，Windows 打包和队友复刻更稳定。
- 不需要额外服务进程，部署简单。
- 后续数据量扩大时再迁移专业向量库也不晚。

RAG v1 的主要链路如下：

```text
用户问题
-> 当前景区过滤
-> query embedding
-> SQLite JSON 向量召回
-> 关键词召回补充
-> 相似度重排
-> 过滤非导览内容
-> 生成带引用约束的回答
```

Embedding 配置采用 OpenAI 兼容接口，模型使用 `BAAI/bge-m3`。系统支持缺 Key 或接口失败时自动降级到关键词和模板逻辑，保证演示不中断。

这一阶段新增了 RAG 状态接口和管理端重建索引能力：

- `POST /api/admin/rag/rebuild`
- `GET /api/admin/rag/status`

这样答辩时可以直接说明：系统不是只靠关键词匹配，而是具备正式的向量召回和本地知识库约束。

## 8. 阶段六：主模型策略从“模型优先”调整为“本地优先，模型补救”

项目接入了 GLM-5.1 作为中文主模型。最初曾考虑让主模型成为第一选择，但测试中发现，景区导览场景不适合完全依赖大模型自由回答。

主要原因是：

- 大模型可能在事实问题上补充未验证信息。
- 路线推荐如果由大模型自由发挥，容易偏离景区知识库。
- 导览类回答需要稳定、可解释、可复现。
- 评审关注事实准确率，不能只看语言自然度。

因此策略调整为：

- 礼仪、路线、泛推荐问题优先走本地模板。
- 普通知识问答优先走 RAG 和本地摘要。
- 本地结果不可靠时，再用主模型进行表达补救或组织语言。
- 主模型输出仍需受检索引用约束，不能绕开知识库。

这个调整是项目中一次重要自纠：不是模型越靠前越好，而是“知识库可控性 + 大模型表达能力”的组合更适合景区问答。

## 9. 阶段七：独立英文回答服务

为了增加国际游客导览能力，项目加入英文回答功能。设计上没有复用中文主模型配置，而是拆分为独立英文服务：

- `ENABLE_ENGLISH_TRANSLATION`
- `ENGLISH_MODEL_API_KEY`
- `ENGLISH_MODEL_BASE_URL`
- `ENGLISH_MODEL_NAME`
- `ENABLE_ENGLISH_TTS`
- `ENGLISH_TTS_VOICE`

前端交互设计为：英文按钮始终显示，但未配置时置灰；配置后点击展开英文讲解；如果英文 TTS 可用，则显示“播放英文”按钮。

这样做的原因是：

- 中文主问答不能被英文翻译服务影响。
- 英文属于增强能力，应该可开可关。
- 答辩时可以清楚说明中英文是两条独立链路。
- 未配置时游客端不应该弹出技术错误。

## 10. 阶段八：GLM-4.5V 图片识别导览

赛题明确要求至少使用一个多模态大模型作为核心 AI 能力支撑。为了提供硬证据，项目新增了“拍照/上传景区图片识别讲解”闭环。

视觉模型选择 GLM-4.5V，原因是当前中转 `/models` 中可用模型名为大写 `GLM-4.5V`，而小写模型名会出现 `ModelNotFound`。视觉链路独立于中文主问答配置：

- `ENABLE_VISION_GUIDE=true`
- `VISION_MODEL_BASE_URL=https://api.edgefn.net/v1`
- `VISION_MODEL_NAME=GLM-4.5V`
- `VISION_MODEL_TIMEOUT_SECONDS=20`
- `VISION_IMAGE_MAX_MB=8`

新增接口：

```text
POST /api/chat/image
```

图片导览的策略是：视觉模型只负责图像观察和候选景点识别，不直接编造景区事实。识别结果再进入现有 RAG 链路，由本地知识库提供事实依据。

链路如下：

```text
游客上传图片
-> GLM-4.5V 识别画面和候选景点
-> 与本地景区景点列表匹配
-> 构造导览问题
-> RAG 检索知识库
-> 生成中文讲解
-> 数字人语音/视频表达
```

这样答辩时可以清楚说明：多模态大模型负责视觉感知，RAG 负责事实准确，数字人负责表达呈现。

开发中曾遇到 `/api/chat/image` 500 问题，根因包括：

- Windows 环境变量 `no_proxy=...::1/128` 影响 `httpx` 代理解析，导致 `Invalid port ':1'`。
- 中转模型名必须使用 `GLM-4.5V`，不能使用小写。

修复策略是在视觉请求中设置 `trust_env=False`，并统一使用大写模型名，同时增强错误处理，避免裸 500 暴露给游客。

## 11. 阶段九：语音生成与响应延迟优化

项目早期使用 Edge TTS 同步生成 MP3，音质较好，但实测服务端生成语音常常需要 11 到 13 秒。这会导致游客等待过久，无法满足“语音问答延迟控制在合理范围内”的要求。

经过排查，真正慢的不是文本问答，而是 TTS 生成。文本首答通常可以在 1 秒内完成，因此优化方向从“换问答模型”改为“语音链路解耦和加速”。

主要优化包括：

### 11.1 文本首答和语音生成解耦

`/api/chat/text` 和 `/api/chat/voice` 先返回文字答案，音频由后台异步任务生成。前端轮询：

```text
GET /api/chat/audio/{log_id}
```

这样用户先看到答案，页面耗时显示“首答耗时”，而不是把 TTS 等待时间算进去。

### 11.2 浏览器本地朗读优先

前端优先使用浏览器 `speechSynthesis` 本地朗读。只要本地朗读可用，就不等待服务端 MP3。朗读开始后，数字人根据本地语音节奏和音频状态做口型动画。

### 11.3 服务端音频回退

当本地朗读不可用、手机 WebView 不支持、或用户明确需要服务端音频时，系统再请求服务端异步 MP3。

### 11.4 Edge TTS 缓存

为减少重复问题的语音等待，项目加入 Edge TTS 确定性缓存。缓存键由以下内容计算：

```text
文本内容 + voice_name + TTS_MAX_CHARS + edge_tts + cache_version
```

缓存文件写入：

```text
data/generated/audio/cache/
```

命中缓存时无需再次调用 Edge，音频可近乎即时返回。项目还新增预热脚本，将 50 题评测集、热门问题、推荐 chip、路线模板和欢迎语提前生成缓存。

### 11.5 MOSS-TTS-Nano 本地试验

项目尝试过 MOSS-TTS-Nano ONNX CPU 方案，目标是在服务端本地生成中文语音，减少对 Edge TTS 的依赖。该方案被设计为独立 `.venv_tts` 和 sidecar，避免污染主项目。

试验结论是：MOSS 在当前 Windows CPU 环境下未稳定达到 5 秒内目标，因此没有进入主展示链路。最终主线保留为：

```text
浏览器本地朗读优先
-> 服务端异步音频回退
-> Edge TTS 缓存优先
-> Edge TTS 兜底生成
```

## 12. 阶段十：数字人路线更迭

数字人是本项目中迭代最多、争议最大的一部分。早期为了快速演示，曾尝试过 2D SVG、卡通形象、面部关键点 Rig、PNG 立绘和口型动画。但实际效果无法达到“真人数字人”的预期，尤其在视觉上容易显得粗糙或恐怖谷。

### 12.1 2D/SVG 原型阶段

早期方案包括：

- 自制 SVG 数字人。
- CSS 表情动画。
- Web Audio RMS 驱动嘴部开合。
- Rhubarb Lip Sync 作为可选 mouth cues 方案。
- 2D 仿生面部关键点 Rig 原型。

这些方案的价值是证明了“参数驱动口型和表情”的技术路线，但问题也很明显：

- 美术质量不足。
- 游客端观感不稳定。
- 用户明确不接受内置 2D 数字人作为最终方案。
- 继续自研人物模型投入大，产出不确定。

因此 2D 原型被保留为技术兜底和说明材料，不再作为主要视觉路线。

### 12.2 OpenAvatarChat 评估阶段

后续评估了 OpenAvatarChat。完整 OpenAvatarChat UI 运行在 `8282`，具备摄像头、RTC、LLM、ASR、数字人等完整链路。但直接接入完整页面存在明显问题：

- 它包含大量本项目已经实现的能力，会和 A5 的 RAG、问答、后台重复。
- 摄像头和实时交互不是当前景区导览的核心需求。
- 资源占用较高，曾出现显存压力和系统卡死风险。
- iframe 平铺外部页面不属于深度融合，观感像拼接。

因此项目没有采用完整 OpenAvatarChat UI，而是抽离 LiteAvatar 数字人渲染能力。

### 12.3 LiteAvatar avatar-only sidecar 阶段

当前数字人主线调整为：

```text
A5 问答/RAG
-> A5 生成中文语音
-> LiteAvatar avatar-only sidecar
-> 输出真人数字人讲解 MP4
-> A5 游客端舞台播放
```

sidecar 地址：

```text
http://127.0.0.1:18085
```

当前保留的核心文件包括：

- `D:\OpenAvatarChatLab\OpenAvatarChat\sidecars\a5_liteavatar_avatar_only.py`
- `D:\OpenAvatarChatLab\OpenAvatarChat\run_a5_liteavatar_avatar_only.ps1`
- `D:\software\frontend\assets\avatar\liteavatar-standby-loop.mp4`
- `D:\software\frontend\assets\avatar\liteavatar-standby.jpg`
- `D:\software\scripts\ensure_avatar_only_sidecar.ps1`
- `D:\software\scripts\check_avatar_only_sidecar.ps1`

这一路线不使用摄像头，不接管 A5 的 LLM、RAG、ASR 或后台，只把“输入音频生成会动、有口型的人物视频”作为能力接入。这样既满足用户对真人数字人的要求，又避免把项目拖入完整 OpenAvatarChat 的资源风险。

### 12.4 待命层与讲解视频融合

为了避免游客端出现“文字先出现、数字人愣住等待视频”的割裂感，前端做了交互调整：

- 待命状态播放 LiteAvatar 静音动态待命视频循环。
- 用户提问后显示“正在思考...”。
- 系统等待数字人讲解视频生成或达到最大等待时间。
- 视频准备好后再展示回答文字，并播放口型讲解 MP4。
- 如果视频生成失败，则回退文字和语音。

这样给游客的感受更接近“数字人正在组织讲解”，而不是“网页先出字、视频后补丁”。

## 17. 当前不足与风险

项目当前仍需如实说明以下不足：

### 17.1 数字人仍依赖 sidecar

LiteAvatar avatar-only 已经比 2D 原型更符合预期，但它不是完全内嵌到 A5 后端里的轻量组件。它需要单独启动 sidecar，并依赖本地 OpenAvatarChat 实验目录。演示前必须确认 `18085` 服务已启动并预热。

### 17.2 语音和视频耗时仍受环境影响

浏览器本地朗读可以最快开始播报，但服务端 MP3 和 LiteAvatar MP4 生成仍受 CPU、内存、模型加载、缓存命中和系统状态影响。常见问题可通过缓存预热优化，但首次冷启动不能保证总是很快。

### 17.3 GLM 和 Embedding 依赖外部中转

主模型、视觉模型、Embedding、英文翻译等依赖外部 OpenAI 兼容接口。Key、余额、限速、网络波动都会影响增强能力。因此系统保留本地模板和 RAG 降级，但多模态识别等功能在无模型服务时无法完整展示。

### 17.4 自建评测不等同于官方评测

50 题自建测试集用于开发回归，当前结果很好，但正式准确率仍应以老师或专家测试集为准。答辩时必须避免夸大。

### 17.5 发行版仍需进一步整理

当前可以提交源码包、文档、演示视频和部署说明，但若要做真正面向普通用户的一键发行版，还需要继续处理：

- 统一启动器。
- sidecar 自动拉起稳定性。
- 模型权重和缓存目录管理。
- API Key 配置界面。
- 公网部署和 HTTPS 域名。
- 日志清理和异常提示。

2. 预热 Edge TTS 缓存和 LiteAvatar 常见问题视频。

5. 答辩时重点展示：图片识别、RAG 问答、数字人讲解、后台评测。

中期如果继续做成简历项目，建议优先：

1. 将 LiteAvatar sidecar 启动流程做得更稳定。
2. 补充 Docker 或一键脚本，但不要把重模型塞进主项目。
3. 做公网 H5 部署，解决非局域网访问问题。
4. 将知识库支持扩展到多景区。
5. 增加 GPS 或定位失败场景方案。
6. 增加演示视频和架构图，让简历项目更容易被理解。

长期如果做产品化，需要进一步：

1. 替换演示 token 为正式权限体系。
2. 使用正式对象存储保存音频、视频和图片。
3. 将 SQLite 升级为可扩展数据库。
4. 引入更稳定的低延迟 TTS 或流式数字人服务。
5. 完善多租户景区配置、审计日志和运维监控。
