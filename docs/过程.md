# 景区导览 AI 数字人项目过程说明

## 1. 文档定位

本文档用于梳理本项目从开始到当前阶段的整体思路更迭、技术选择原因、功能推进顺序和自纠过程。它不是单纯的操作手册，也不是接口清单，而是说明项目为什么会从一个赛题想法逐步演变为当前这套“游客端 H5 + 管理端后台 + FastAPI 智能服务 + 可选数字人增强”的完整闭环系统。

项目题目方向是“景区导览服务 AI 数字人”。当前演示景区为灵山胜境，但系统定位不是只能服务灵山胜境的固定问答页面，而是一个可配置景区知识库、数字人形象和服务能力的导览平台。灵山胜境在本项目中承担的是示范数据和演示场景作用。

## 2. 最初需求理解：先明确题目到底要什么

项目开始时，最重要的问题不是马上写代码，而是先拆解赛题要求。题目表面上包含“数字人”“多模态交互”“智能问答”“个性化推荐”“后台管理”“数据看板”等多个方向，如果直接追求一个很炫的数字人形象，很容易忽略真正的验收重点。

经过分析后，项目被理解为一个智慧景区导览系统，而不是普通聊天机器人，也不是单纯虚拟形象展示。核心能力应当包括：

- 游客能通过文字或语音提出景区相关问题。
- 系统能基于景区知识库给出导览式回答。
- 数字人能够用语音、表情和口型动画进行回应。
- 游客能获得路线推荐、礼仪提示、景点讲解等服务。
- 管理者能维护知识库、查看日志和运营数据。
- 系统具备可演示、可验收、可扩展的工程闭环。

因此，最初的总体策略确定为“先做闭环，再做增强”。也就是说，先把后端、数据库、知识库、问答、前端展示、管理端和基础语音串起来，再逐步增强 RAG、数字人表现、移动端 H5、发行版和本地 TTS。

## 3. 第一阶段选择：先做 A 端能力底座

最初两人分工时，本人负责 A 端，也就是后端与智能服务能力。A 端的定位不是只写几个接口，而是整个系统的能力底座。前端游客页、管理端页面、后续发行版和演示验收，都依赖 A 端提供稳定数据。

这一阶段选择了 FastAPI + SQLite + 静态前端挂载的方式。原因主要有三点：

- FastAPI 自动生成接口文档，方便自己测试，也方便队友联调。
- SQLite 部署轻量，不需要额外安装 MySQL、PostgreSQL 等数据库，适合比赛演示和 Windows 打包。
- 静态前端由 FastAPI 统一挂载到 `/app/`，可以减少跨域、端口和部署复杂度。

没有一开始选择复杂微服务、Docker 集群或企业级数据库，是因为当时最关键的是尽快证明系统能跑通。比赛项目时间有限，若过早引入复杂基础设施，会把大量精力消耗在环境配置上，反而影响核心功能完成。

## 4. 第二阶段选择：先用轻量知识库和规则模板打通问答

最早的问答能力并不是正式 RAG，而是基于样例景点数据、知识片段和关键词匹配做本地回答。这一选择不是因为关键词检索最强，而是因为它最容易形成稳定闭环。

当时的目标是先让系统能够回答典型问题，例如：

- 灵山胜境在哪里？
- 九龙灌浴几点开始表演？
- 灵山大佛有什么文化含义？
- 半天时间应该怎么游览？

采用轻量检索和模板回答的原因是：

- 景区官方资料规模不大，前期不需要立即上向量数据库。
- 规则和模板可控，适合演示，避免大模型胡乱推荐。
- 可快速发现知识库字段、景点名称、路线数据是否合理。
- 方便前端先接入并展示问答结果。

这一阶段也暴露出问题：简单关键词匹配容易出现跨景区误命中、字段说明被当作导览内容、回答和问题不完全对应等情况。这些问题后来推动了正式 RAG、景区过滤和二次校验机制的加入。

## 5. 第三阶段选择：路线推荐先采用规则和预设路线

题目要求个性化推荐，但如果一开始就做复杂推荐算法，会面临数据不足的问题。真实推荐系统通常需要大量用户行为、停留时间、点击记录和历史偏好，而当前比赛项目没有这些长期数据。

因此路线推荐第一版采用“兴趣关键词 + 游览时长 + 预设路线”的方案。比如历史文化、佛教文化、自然风光、亲子休闲等方向分别对应不同路线。后来又增加 `user_id`，使推荐可以结合游客最近问答日志和兴趣关键词，形成轻量个性化说明。

这样选择的原因是：

- 输出稳定，便于答辩演示。
- 老师容易理解推荐依据。
- 数据不足时不强行包装成复杂算法。
- 后续如果有真实游客行为，可以在当前结构上继续升级。

这一阶段形成了“用户输入兴趣 -> 后端匹配路线 -> 前端展示路线卡片”的闭环，也让游客端不只是问答页面，而更像一个导览服务入口。

## 6. 第四阶段选择：B 端缺位后转为全栈补齐

前端一开始采用原生 HTML、CSS、JavaScript，而不是 Vue、React 或复杂组件库。原因是：

- 当前项目页面结构可控，原生实现足够支撑演示。
- 不新增构建链路，降低 Windows 本地运行和打包风险。
- FastAPI 可直接挂载静态文件，部署简单。
- 修改反馈速度快，适合频繁根据页面效果调整。

前端先完成游客端问答、语音上传、路线推荐、反馈评价，再补管理端登录、看板、日志、知识库管理和数字人配置。这个顺序延续了“先闭环、再美化”的原则。

## 7. 第五阶段选择：数字人先做可控 2D 方案，而不是强上 3D 或 Live2D

项目中反复讨论过数字人形象：是否要做真正 Live2D、是否仿照虚拟偶像、是否做桌宠式角色、是否接外部视频数字人。最终当前版本采用的是原创 2D 立绘 + 前端 SVG/CSS 动效 + Web Audio 口型驱动 + 可选外部视频服务。

没有直接使用初音未来、B 站虚拟偶像或其他第三方 IP 素材，是因为版权风险很高。比赛提交不能依赖未授权素材，因此数字人形象必须是自制或可授权替换。

没有一开始直接接 Live2D Cubism SDK，是因为：

- Live2D 模型需要分层绘制、绑定参数和 SDK 接入，制作成本高。
- 当前项目重点是导览问答闭环，而不是虚拟偶像制作。
- 两人项目时间有限，强上 Live2D 可能导致核心问答和后台功能不稳定。
- 后续可以保留接口和素材管理能力，再升级为正式 Live2D。

当前方案的逻辑是：游客端始终能看到一个数字导览员；播放语音时，前端通过音频 RMS 振幅驱动嘴部、头部、光效和状态动画；如果后续外部数字人视频服务可用，则优先播放视频，失败时回退音频和 2D 动效。这样既满足“语音、表情和口型同步”的可演示要求，又避免把项目卡死在重模型或版权素材上。

## 8. 第六阶段选择：从关键词问答升级到正式 RAG v1

随着测试问题增多，简单关键词检索的问题越来越明显。比如系统有时能检索到相关片段，却没有按照问题准确回答；或者泛推荐问题被不相关景区、字段规范、数据集说明带偏。

因此问答层进行了正式 RAG v1 升级。选择的方案是 SQLite JSON 存向量，而不是 Chroma、FAISS 或 Milvus。原因是：

- 当前知识库规模不大，SQLite JSON 足够演示。
- Windows 打包和部署更稳定，不需要额外向量数据库服务。
- 避免引入大型依赖导致队友或评审机器无法运行。
- 后续如果数据规模扩大，再迁移到专业向量库也不迟。

RAG 升级后的主要变化包括：

- 先按当前景区过滤知识范围。
- 使用 Embedding 生成知识片段向量。
- 用余弦相似度召回 topK。
- 保留关键词召回作为补充。
- 过滤字段规范、景点 ID、数据集说明等非导览内容。
- 泛推荐和路线问题继续优先走稳定模板。
- 无可靠引用时明确提示知识库未查到，不编造。

这个阶段的思路更迭很关键：系统从“能答”升级为“尽量基于资料答”，同时保留模板兜底，避免大模型或向量检索在演示中失控。

## 9. 第七阶段选择：问答策略从主模型优先转为本地优先、模型补救

在接入 GLM-5.1 中转模型后，曾经考虑过让主模型成为第一选择。但测试后发现，如果主模型直接生成回答，可能会出现不按知识库回答、推荐不稳定或答非所问的情况。

因此策略调整为“本地模板和 RAG 优先，主模型只做补救”。也就是说：

- 礼仪、路线、泛推荐等高风险问题优先走本地模板。
- 普通知识问答先走 RAG 和本地摘要。
- 如果本地回答校验不可靠，再短超时调用主模型修复。
- 主模型回答仍要经过引用校验，不能随意放行。

这样选择的原因是：

- 景区导览需要稳定、可解释，不是自由闲聊。
- 本地模板能确保路线推荐不跑偏。
- RAG 引用能说明答案来自知识库。
- 主模型作为补救可以提升表达质量，但不能取代知识约束。

这也是项目自纠中很重要的一次转向：不是“模型越强越好”，而是“可控、稳定、能解释”更适合导览场景。

## 10. 第八阶段选择：英文回答独立服务，不复用中文主链路

后续增加了英文回答按钮。最初可以简单把中文回答丢给同一个主模型翻译，但这样会造成配置混乱：中文问答和英文翻译共用 Key、模型和失败状态，一旦英文服务异常，可能影响中文主流程。

因此英文回答被拆成独立配置：

- `ENGLISH_MODEL_API_KEY`
- `ENGLISH_MODEL_BASE_URL`
- `ENGLISH_MODEL_NAME`
- `ENABLE_ENGLISH_TRANSLATION`
- `ENABLE_ENGLISH_TTS`
- `ENGLISH_TTS_VOICE`

游客端逻辑也做了调整：英文按钮始终可见，但未配置时置灰；配置后点击展开英文文本；如果英文语音生成成功，则在英文块里提供播放按钮。中文问答、中文语音和 RAG 检索不依赖英文服务。

这样选择的原因是：

- 中文主流程必须稳定，不能被英文增强功能拖垮。
- 英文翻译属于附加能力，应当可开可关。
- 演示时可以清楚说明中文和英文是两条独立链路。
- 未配置时游客端不弹出技术报错，更符合真实产品体验。

## 11. 第九阶段选择：语音链路从同步 Edge TTS 改为多级加速

语音播报一开始采用 Edge TTS 同步生成 MP3。这个方案接入快、音质好，但后来实测发现服务端生成语音常常需要 11 秒以上，甚至偶尔失败。若游客必须等待语音生成完成才能看到回答，就无法满足“响应时间小于 10 秒”的验收目标。

因此语音链路经历了三次更迭。

第一步是异步化：文本首答立即返回，TTS 后台生成，前端轮询 `/api/chat/audio/{log_id}`。这样游客先看到答案，不再被音频生成阻塞。

第二步是浏览器本地朗读优先：桌面浏览器支持 `speechSynthesis` 时，前端直接朗读中文回答，同时用本地口型动画驱动数字人。手机、Android WebView 或本地朗读失败时，再请求服务端 MP3。

第三步是本地轻量 TTS 回退试验：新增可选 MOSS-TTS-Nano ONNX sidecar，服务端回退链路变为 `local_moss_onnx -> edge_tts -> failed`。这样未来在手机端或本地朗读不可用时，可以优先使用本机轻量 TTS，而不是完全依赖 Edge TTS。

这个阶段的选择原因非常明确：

- 问答本体很快，慢的是语音生成。
- 首答耗时应统计文字返回时间，而不是把 TTS 等待混进去。
- 浏览器本地朗读是最快、最轻的桌面方案。
- 服务端 TTS 仍要保留，用于手机和回退。
- MOSS ONNX 采用独立 `.venv_tts` 和 sidecar，避免污染主项目环境。

## 12. 第十阶段选择：管理端从辅助页面升级为验收证明

管理端最初只是登录、日志和简单看板。后来发现，很多功能如果只藏在后端代码里，老师无法直观看到。例如 RAG 是否启用、向量索引是否构建、TTS 是否可用、数字人视频服务是否配置、评测准确率是否达标。

因此管理端逐步补齐了：

- 运营数据看板。
- 问答日志。
- 游客感受度报告。
- 知识文档上传、预览、编辑、重导入。
- 知识片段新增、编辑、删除。
- 数字人形象配置和素材上传。
- RAG 向量索引状态和重建按钮。
- AI 能力状态面板。
- 自动验收评测面板。

这样做的原因是：管理端不仅是后台操作入口，也是答辩时证明系统能力的地方。尤其当项目包含 RAG、模型、TTS、口型同步、视频服务等多个能力时，必须有一个地方把系统状态讲清楚。

## 13. 第十一阶段选择：游客端从 Demo 面板重构为 H5 产品页

前端一开始偏功能堆叠，能用但不够像成熟产品。随着功能逐渐完整，页面目标发生变化：从“演示接口是否可用”转向“让老师和游客一眼觉得这是一个完整的 AI 导览产品”。

视觉上经历了几轮调整：

- 早期科技展板风格，用于快速展示功能。
- 后来改成 SaaS Dark Glass 风格，去掉硬线条和网格，增加毛玻璃、深色渐变和数字人舞台。
- 再后来根据移动端访问需求，重构为手机优先 H5，强调游客端体验。
- 保留 B 站截图试验层作为明亮氛围参考，但正式发行仍建议替换为授权素材。

交互上也做了多轮自纠：

- 用户消息和 AI 回答改成更真实的左右气泡。
- 推荐问题从大卡片改成小 chip，减少喧宾夺主。
- 评分从夸张星星改成低调反馈标签。
- 输入区整合为统一输入栏，避免按钮分散。
- 游客端隐藏 Key、RAG、模型名等后台信息。
- 管理端保留技术状态，游客端只保留对游客有意义的能力说明。

这次转向的原因是：比赛项目不仅要功能完整，也要有展示完成度。页面太像调试 Demo，会削弱老师对系统成熟度的判断。

## 14. 第十二阶段选择：发行路径从本地局域网转向公网 H5 与轻量客户端

一开始本地访问是 `127.0.0.1:8000/app/`，手机访问可以通过同一 Wi-Fi 下的局域网 IP。但这只适合开发调试，不适合真实游客使用。游客不可能都连同一个 Wi-Fi。

因此发行思路调整为：

- 真实访问应部署到公网 HTTPS 域名。
- 游客端优先做 H5 页面，手机浏览器直接访问。
- 小程序不是第一优先级，因为审核、平台 API 和适配成本更高。
- Windows 低显卡客户端只打开云端页面，不内置重模型。
- Android WebView APK 可由 GitHub Actions 云端构建，输入公网 `app_url` 后生成安装包。

这样选择的原因是：

- H5 跨平台最快，老师、游客、队友都能直接打开。
- 公网 HTTPS 才符合非局域网访问需求。
- 轻量客户端能满足“发行版”表达，但不增加本机部署负担。
- 数字人视频、ASR、TTS 等重能力应放在云端或可选服务端，不塞进低配设备。

## 15. 安全与协作思路更迭

项目中多次涉及 API Key，例如 Embedding、GLM 中转、英文回答服务。最初为了快速测试，曾在对话中暴露过 Key。之后项目明确了安全原则：

- 密钥只能写入本机 `.env`。
- `.env` 不进入 Git。
- `.env.example` 只写字段模板，不写真实密钥。
- 已暴露过的 Key 应在平台后台重置。
- GitHub 推送前要检查是否误提交敏感信息。

协作上也逐渐形成了交付意识。由于队友不在同一地点，项目需要通过 GitHub、文档和清晰接口进行异地协作。因此补充了：

- A 端开发步骤手册。
- B 端应做指南。
- 前端实现说明。
- 页面自纠检查记录。
- 发行版打包说明。
- 上下文恢复说明。
- 本地 TTS 配置说明。

这些文档的作用不是装饰，而是降低交接成本。即使开启新对话、换机器或队友恢复工作，也能快速知道项目做到哪里、怎么启动、哪些限制必须说明。

## 16. 当前形成的整体闭环

截至当前阶段，系统已经形成以下闭环：

1. 游客通过 H5 页面进入景区导览界面。
2. 游客可输入文本、录音或上传语音。
3. 后端进行语音识别或文本问答。
4. 问答先走模板、RAG、本地校验，必要时由主模型补救。
5. 系统返回答案、引用、情绪、语音状态、数字人视频状态和日志 ID。
6. 前端展示数字人、聊天气泡、语音播放、英文翻译和反馈入口。
7. 游客可以继续生成路线推荐或提交满意度反馈。
8. 管理员可登录后台查看日志、看板、知识库、RAG 状态、数字人配置和评测结果。
9. 如需发行，可走公网 H5、Windows 轻量客户端或 Android WebView APK。

这套闭环覆盖了赛题要求中的多模态交互、智能问答讲解、个性化推荐、后台管理、数据分析和数字人展示。

## 17. 当前仍需主动说明的边界

虽然项目已经形成完整演示系统，但答辩时仍应主动说明边界，避免过度包装：

- 当前数字人不是 3D 建模角色。
- 当前默认不是 Live2D Cubism SDK 模型，而是原创 2D 立绘与前端动效。
- 口型同步是音频振幅驱动，不是逐音素级口型。
- 外部数字人视频服务是可选增强，不是默认强依赖。
- 管理员登录仍是演示级鉴权。
- RAG 使用 SQLite JSON 向量存储，适合当前知识库规模，不是企业级向量数据库。
- 本地 MOSS-TTS-Nano ONNX 属于可选回退试验，需要额外启动 sidecar。
- 如果公开发行，B 站截图试验层和任何第三方素材都应替换为自制或授权素材。

主动说明这些边界并不是扣分点，反而能体现项目对工程真实性、版权风险和部署成本有清晰判断。

## 18. 总结：项目思路的核心变化

从开始到现在，项目最大的变化可以概括为五条：

第一，从“做一个数字人”转为“做一个景区导览服务平台”。数字人不是孤立形象，而是问答、路线、语音、后台和数据的统一展示入口。

第二，从“先追求炫酷效果”转为“先保证可运行闭环”。后端、数据库、接口、前端和管理端先打通，再逐步补强视觉、RAG、语音和发行。

第三，从“模型生成优先”转为“本地可控优先，模型补救”。景区导览要求稳定、可解释、可引用，因此模板和 RAG 必须优先于自由生成。

第四，从“本地演示”转为“面向真实访问和发行”。手机端访问、公网 HTTPS、H5、Windows 轻量客户端和 Android WebView APK 都是围绕交付可用性展开。

第五，从“完成代码”转为“完成可验收系统”。管理端状态、自动评测、文档、启动脚本、回退机制和安全边界，都是为了让项目不仅能跑，而且能被解释、被检查、被交接。

因此，当前项目的价值不只在于某个单点功能，而在于它已经从赛题要求出发，经过多轮自纠和技术取舍，形成了一套比较完整、可演示、可继续扩展的景区导览 AI 数字人系统。
